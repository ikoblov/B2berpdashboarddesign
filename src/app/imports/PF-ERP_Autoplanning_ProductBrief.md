# PF-ERP: Модуль автопланирования
## Продуктовая спецификация и бриф для Figma Make

**Версия:** 1.0
**Дата:** 19 апреля 2026
**Контекст:** Модуль для PeopleFast ERP, закрывающий полный цикл подбора исполнителей на заявки клиентов.

---

## 1. Контекст и бизнес-цели

### 1.1 Задача модуля

**PeopleFast** — компания по подбору рабочих для B2B-клиентов (стройка, уборка, разгрузка). Клиент обращается с заявкой "нужно N человек на дату X на объект Y", модуль должен:

1. **Отобрать** релевантных исполнителей из базы (hard-filters по статусу, гео, доступности)
2. **Проранжировать** их по рейтингу и контекстным факторам (опыт на объекте, у мастера, с типом задач)
3. **Связаться** через каналы (Telegram → МАКС → IVR → SMS → куратор)
4. **Собрать ответы** и поставить смены
5. **Балансировать** распределение, чтобы не концентрировать лучших на одной заявке

### 1.2 Стратегические цели

- **Снизить нагрузку на кураторов** — сейчас куратор вручную обзванивает и собирает заявку
- **Повысить стабильность явки** — прогнозировать дефицит заранее и собирать резерв
- **Улучшить compliance по ФНС** — % самозанятых (НПД) на заявке = ключевая метрика
- **Перейти к платформенной модели** — в Phase 2 модуль работает параллельно с marketplace, где исполнители сами подбирают заявки

### 1.3 Пользователи модуля

| Роль | Что делает |
|---|---|
| **Куратор** (менеджер планирования) | Создаёт заявки, смотрит прогноз, одобряет подбор, решает экстренные ситуации |
| **Менеджер подбора персонала** | Добавляет новых исполнителей, проставляет верификацию, оставляет мнения |
| **Исполнитель** | В боте отмечает готовность, принимает/отклоняет предложения, смотрит кошелёк бонусов |
| **Мастер клиента** | В боте оценивает исполнителей после смены (👍/neutral/👎) |
| **Клиент** (Phase 2) | Создаёт заявки через ЛК, видит прогноз, выбирает предпочтительного foreman |

## 2. Ключевые концепции

### 2.1 Градации заявок по времени на подбор

**Главный принцип:** учитываем **чистое время на подбор**, исключая ночное окно **21:00–07:00** (когда звонить нельзя).

| Тип | Чистое время на подбор | Поведение системы |
|---|---|---|
| **Предварительная** | > 24 ч | Фоновая пересборка раз в сутки, резерв формируется заранее |
| **Плановая** | 4–24 ч | Стандартный flow: волны, Telegram-бот, IVR по таймауту |
| **Срочная** | 1–4 ч | Сжатые таймауты, приоритет today-pool, сразу IVR |
| **Прямо сейчас** | < 1 ч | Только today-pool + ближайшие (пешком/машина), мгновенный IVR |

**Пример:** заявка подана в 19:00 на 08:00 следующего дня.
- Формально: 13 часов до начала
- Из них 10 часов ночного окна (21:00–07:00)
- **Реальное время на подбор: 3 часа = срочная**

**Ночное окно 21:00–07:00:** подбор не ведётся. Заявки ночью **пока не принимаются** (фича отложена до запуска 24/7-режима).

### 2.2 Health Score и зоны (светофор)

Каждая заявка имеет **композитный health score** (0–100) + разбивку по факторам:

```
Заявка #1234 │ ЖК "Восток" │ 15.05, 08:00 │ 15 человек

🟡 Оранжевая зона (Health Score: 67/100)

├─ 📊 Закрытие: 12/15 (80%) 🟡
├─ 👥 НПД: 60% (9/15) 🟡
├─ 🎯 Прогноз явки: 78% 🟡
├─ ⭐ Рейтинг состава: 6.2/10 🟢
└─ 👨‍👩‍👧 Возрастной баланс: ОК 🟢
```

**Пороги:**
- 🟢 **Зелёная:** Health Score ≥ 85
- 🟡 **Оранжевая:** 60–84
- 🔴 **Красная:** < 60

Зона влияет на:
- **Overbooking factor** (🟢 ×1.1, 🟡 ×1.3, 🔴 ×1.6)
- **Приоритет в дашборде** (красные всегда сверху)
- **Автоматическую эскалацию** куратору при < 60

### 2.3 Пресеты приоритета подбора

Каждая заявка имеет пресет, определяющий, **как именно** ранжировать кандидатов.

| Пресет | Когда применяется | Что приоритизирует |
|---|---|---|
| **Стандарт** | По умолчанию | Комплексный скор (рейтинг + контекст + дистанция) |
| **Срочно** | Автоматически при <4ч | **Расстояние** в первую очередь (пешком > автобус > авто) |
| **Качество** | Автомат при "новый объект" | **Лучшие из лучших** (максимальный рейтинг) |
| **После жалобы** | Автомат: unresolved complaint <7 дней | Качество + overbooking ×1.5 |
| **Показательная** | Вручную куратором | То же что "качество", но с квотой "только verified" |

Куратор всегда может **переопределить** пресет вручную при создании заявки.

### 2.4 Статусы исполнителей

**Три независимых измерения:**

**1. Лояльность (история работы)**
- `new` — первая смена
- `returning` — есть история, перерыв > 30 дней
- `active` — регулярно работает (последняя смена < 30 дней)

**2. Верификация** (отдельный флаг `is_verified`)
- `False` — документы не проверены
- `True` — паспорт и документы подтверждены куратором

**3. Готовность к работе (динамическая)**
- `availability_date` — список дат, когда готов выйти (например, `[2026-05-17, 2026-05-18]`)
- `ready_now` — флаг "готов прямо сейчас" + timestamp (действует 4 часа)
- `blacklist` — в чёрном списке
- `archived` — в архиве (неактивен)

**Логика оплаты** (следствие из статуса лояльности):
- `new` и `returning` → **день в день** (вечер той же смены) — как стимул
- `active` → **следующий день** (12ч отсрочка как привилегия)

### 2.5 Волны подбора

**Порядок обработки при подборе:**

| Волна | Кого включаем | Когда запускаем |
|---|---|---|
| **Волна 0: Today-pool** | Готовы сегодня + лишние с объектов + "прямо сейчас" отклики | Только для срочных заявок |
| **Волна 1: Явно готовы** | `availability_date` содержит нужную дату | Всегда первая |
| **Волна 2: Активные 7 дней** | Выходили или отмечались за последние 7 дней | Если Волна 1 дала <70% нужного |
| **Волна 3: Активные 30 дней** | Выходили за последние 30 дней | Если Волна 2 недостаточно |
| **Волна 4: Вся база** | Все, кроме blacklist/archived | Крайний случай, массовая рассылка |

**Переключение между волнами:**
- **По результату** (основной режим): собрали ответы → если дефицит, запускаем следующую волну
- **По таймеру** (для срочных): через 30 мин без достаточного ответа — следующая волна

### 2.6 Today-Pool (динамический резерв на сегодня)

Пул исполнителей, **доступных в ближайшие часы**. Обновляется в реальном времени.

**Кто попадает:**
1. Отметили "готов сегодня" в боте
2. Лишние на объекте (разворот) — автоматически на 3 часа после разворота
3. Ответили "да" на "появилась срочная — готов?"

**Как используется:**
- При срочной/прямо-сейчас заявке — ищем **только в today-pool первые 15 минут**, потом расширяем
- В дашборде видно: "В today-pool: 23 чел, ближайшие — в 2 км от объекта"

### 2.7 Балансировка (greedy round-robin)

**Проблема:** если 10 заявок на день и Иванов с рейтингом 0.95 подходит под все, куда его ставить?

**Решение (MVP):**
1. По всем активным заявкам собираем топ-кандидатов
2. **Первый проход:** распределяем по 1 лучшему на каждую заявку
3. **Второй проход:** по 1 из второго эшелона
4. И так далее, пока все заявки не закрыты

**Ограничение:** один исполнитель — максимум на одну заявку в день. Исключение: утренняя + вечерняя смена в разных местах.

### 2.8 Оценка мастером и рейтинг

**Мастер** (контактное лицо клиента на объекте) после смены оценивает каждого исполнителя:

| Оценка | Что происходит |
|---|---|
| 👍 **Отлично** | Буст на этого мастера (preferred) + +0.5 к глобальному рейтингу |
| ➖ **Нормально** (default) | Ничего не меняется |
| 👎 **Плохо** | Бан на этого мастера (banned) + -0.8 к глобальному рейтингу |

**Защита от предвзятости (z-score):**
- Если мастер ставит 👍 всем подряд — вес его оценки снижается
- Если мастер ставит 👎 всем — вес его оценки тоже снижается, но негативная оценка остаётся как warning-флаг
- Нормализация через z-score по всем оценкам этого мастера

**Глобальный рейтинг снижается** если 5+ разных мастеров поставили 👎 → auto-flag куратору на review.

### 2.9 Мнения (Opinion)

**Отдельная от оценки сущность.** Это свободный текстовый комментарий, который **не влияет на скор автоматически**, но показывается куратору при подборе.

**Кто может оставлять:**
- Куратор (первое впечатление)
- Менеджер подбора персонала
- Мастер (дополнительно к оценке)
- Другие исполнители (коллеги)
- Анонимный источник (через спец. форму)

**Severity:**
- `info` — просто информация ("любит кофе, разговорчивый")
- `warning` — внимание ("конфликтовал с бригадой на объекте X")
- `critical` — критично ("был в алкогольном опьянении, 12.03")

### 2.10 Foreman (старший смены)

**На каждой заявке обязательно** должен быть назначен foreman. Это исполнитель, который:
- Встречает бригаду утром
- Координирует с мастером клиента
- Отчитывается о явке
- Получает доплату (настраивается на уровне заявки)

**Флаг `can_be_foreman` у исполнителя:**
- Ставится **однократно куратором** после оценки кандидата
- Критерии для ручной оценки (подсказка системы): 20+ смен, положительные мнения мастеров, стабильная явка

**Авто-выбор foreman при подборе:**
1. Берём всех подобранных кандидатов с `can_be_foreman = True`
2. Ранжируем по: опыт на объекте → рейтинг → опыт с мастером
3. Top-1 = foreman
4. Если отказался — автоматически следующий из списка
5. Если никого нет — флаг `⚠️ нет foreman` в заявке, куратор решает вручную

**Preferred foreman от клиента:**
- В заявке опциональное поле `preferred_foreman_id`
- Если клиент указал и этот foreman доступен — ставим его приоритетно

## 3. Модели данных (обзор — детали в отдельной спеке)

### 3.1 Новые модели

- **`WorkerOpinion`** — мнение от любого источника (мастер/куратор/коллега/аноним)
- **`WorkerMasterRelation`** — статус связки (banned/preferred/neutral) + счётчик смен
- **`WorkerObjectRelation`** — личные предпочтения по объектам (isolation/bonus)
- **`WorkerBonus`** — виртуальный кошелёк (начисления и списания)
- **`ShiftOffer`** — state machine предложения смены исполнителю
- **`ClientComplaint`** — жалобы клиентов (влияют на пресет следующей заявки)
- **`FirstImpression`** — оценка куратора при первом знакомстве (seed для рейтинга)
- **`TodayPoolEntry`** — запись в today-pool (worker_id, entered_at, expires_at, source)

### 3.2 Изменения существующих

- **`Worker`**: добавляем `loyalty_status` (new/returning/active), `is_verified`, `can_be_foreman`, `gender`, `birth_date`, `has_car`, `accepts_physically_hard`, `accepts_evening_shifts`, `accepts_night_shifts`, `coordinates` (если нет)
- **`RequestLine`**: `priority_preset`, `gender_required`, `is_physically_hard`, `foreman_id`, `preferred_foreman_id`, `foreman_bonus_amount`
- **`DailyRequest`**: `health_score`, `zone` (green/yellow/red), `npd_percent`, `show_up_prediction`
- **`DailySnapshot`**: расширить аналитическими полями

## 5. UX-сценарии (user flows)

### 5.1 Flow "Создание и автоподбор заявки"

1. Куратор нажимает **"+ Создать заявку"** на дашборде
2. Заполняет форму, видит **live preview** прогноза
3. Нажимает **"Создать"**
4. Система:
   - Создаёт `DailyRequest` и `RequestLine`
   - Запускает алгоритм подбора (Волна 1)
   - Создаёт `ShiftOffer` для top-N кандидатов
   - Отправляет предложения в Telegram-бот
5. Куратор перенаправляется на **экран подбора**
6. В реальном времени видит: кто получил, кто принял, кто отказался
7. Если через 30 мин дефицит — система **автоматически** запускает Волну 2
8. Куратор может вмешаться: добавить кандидата вручную, переопределить foreman
9. Когда 100% закрыто — заявка переходит в статус **"Расстановка готова"**
10. Утром foreman получает уведомление "ты старший, объект Y"

### 5.2 Flow "Эскалация по красной зоне"

1. Система видит: заявка в 🔴 красной зоне + дефицит > 50%
2. **Автоматически** уведомляет куратора (push + звук)
3. Предлагает варианты:
   - Поднять ставку (+10%, +15%)
   - Расширить радиус поиска
   - Запустить массовую рассылку
4. Куратор выбирает вариант (или делает что-то своё)
5. Система применяет решение, пересчитывает прогноз

### 5.3 Flow "Исполнитель — лишний на объекте"

1. Мастер в 08:15 сообщает куратору: "Приехало 16, надо было 15, один лишний"
2. Куратор открывает заявку, помечает Иванова как **"лишний"**
3. Система:
   - Проверяет другие заявки на сегодня в радиусе 10 км
   - Предлагает куратору: "Есть дефицит на парковке Лента в 2 км, перекинуть Иванова туда?"
4. Куратор соглашается
5. Система уведомляет Иванова через бота: "Можем перекинуть на другой объект, согласен?"
6. Иванов принимает → едет на новый объект
7. Если не перекинули — Иванов едет домой, попадает в **today-pool** на 3 часа
8. Куратор может начислить бонус за неудобство

### 5.4 Flow "Мастер оценивает исполнителя"

1. После завершения смены мастер получает уведомление в боте
2. Показываются фото+ФИО каждого члена бригады
3. Для каждого мастер нажимает 👍 / ➖ / 👎 (Tinder-стиль)
4. Система сохраняет оценку в `WorkerMasterRelation`
5. Если 👎 — появляется поле "Комментарий" (становится `WorkerOpinion` с severity=warning)
6. Система пересчитывает глобальный рейтинг исполнителя

### 5.5 Flow "Прогноз и ручная рассылка"

1. Куратор открывает **Supply/Demand Dashboard**
2. Видит: на выходные дефицит > 50%
3. Нажимает **"Запустить рассылку"**
4. Система показывает превью: "Рассылка будет отправлена 256 исполнителям"
5. Куратор подтверждает → рассылка уходит через Telegram/МАКС
6. Ответы накапливаются → прогноз обновляется в реальном времени

- Primary BG `#FFFFFF` — основной фон

- Закруглённые (pill shape)

## 8. Метрики успеха

### 8.1 Продуктовые

- **Health Score среднее по заявкам**: цель ≥ 75 (сейчас ~55)
- **% заявок в зелёной зоне**: цель ≥ 60% (сейчас ~30%)
- **Время от создания заявки до 80% закрытия**: цель < 2 часов (сейчас ~6 часов)
- **% автоматических подборов** (без вмешательства куратора): цель > 50%

### 8.2 Бизнесовые

- **Стабильность явки**: > 85% на заявке (сейчас ~70%)
- **% НПД на заявке**: в среднем ≥ 80% (для ФНС-compliance)
- **Нагрузка на куратора**: < 1.5 часа в день на обзвоны (сейчас ~4 часа)

### 8.3 Исполнительские

- **Churn rate**: < 10% в месяц
- **Среднее количество смен на активного**: ≥ 8 в месяц
- **Retention через 90 дней**: > 60%
